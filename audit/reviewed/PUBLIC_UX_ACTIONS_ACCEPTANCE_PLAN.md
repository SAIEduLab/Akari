# あかり 1.0.2 UX受入とActions検証計画

本書は、あかりの制作体験の受入基準と、GitHub Actionsで検証する機械的な範囲を定める。中心となるのは、小学生がイメージしたことを国語教育として正しく自然な日本語で書き、その意図どおりに実現できる制作体験である。ブロックで直感的に作れること、コードとブロックの意味が完全に一致すること、既存機能を減らさないことも必須とする。

本書は製品の受入設計であり、検査を実行した結果や製品の合格を報告するものではない。

## 1 受入の目的と非妥協条件

### 1.1 イメージから自然な日本語で実現する

制作前に、作りたいこと、実行前の予想、観察すべき結果を固定する。その後、文法例や製品が受理する定型文を見る前に作成した原作文を使う。既存の凍結済み原作文を再利用する場合は、原文と期待の識別情報を維持する。

原作文は、主語と述語、助詞、対象、順序、条件と繰返しの範囲、数量と単位、時間、引用された文字列の意味を点検する。国語として正しく自然で、意図が確定している文は、そのまま受理され、意図した結果になることを必要とする。読みやすい説明があるだけでは、この条件を満たさない。

正しい原文を拒否した場合、その拒否を記録する。別の表現に変更して動いた結果は復旧として別に記録し、原文の拒否を成功へ書き換えない。複数の意味に読める文では、製品が意味を勝手に決めず、分かりやすい確認や案内を行うことを評価する。

### 1.2 機能を保持する

基準版の能力集合、命令、式、イベント、ブロック定義、素材、保存・復元能力、実行能力を保持する。新版の保存契約を保持し、旧契約との互換は必須としない。新機能を追加しても既存機能を削除しない。モード、基本表示、詳細表示を使って機能を隠し、検査対象から外すこともしない。

能力集合と全ブロック定義は、バージョン管理された公開可能な対応表で管理する。基準版との差分には、対応するテストと明確な仕様が必要である。

基準の機械対応は、既存能力260、命令74、式76、イベント32、境界38、ブロック定義164を対象とする。これらは重複を含む要件集合の規模であり、独立した実操作本数や合格数ではない。版の変更で集合が増える場合は差分を追加し、既存IDを無断で減らさない。

### 1.3 コードとブロックの意味を完全に一致させる

対象と所有者、命令の順序、条件と反復の範囲、数値と単位、引用、空の分岐、定義と引数、イベント、分身、保存される作品を保持する。両モードが同じ誤結果になっただけでは合格にしない。製品実装とは独立した期待値と比較する。

無編集の往復では原文保持を、一つのフィールドを編集した往復では変更の局所性と意味の保持を確認する。ブロックから生成したコードの検証に加え、同じ意図を両モードで独立に作る制作体験も確認する。

## 2 実操作と自動検証の役割

| 担当範囲 | 主な方法 | 確認するもの |
|---|---|---|
| 制作UX | 実画面で通常のクリック、入力、配置、実行、修正を行う | 意図からの発見、自然な作文、範囲の理解、迷い、操作の手応え、結果と案内の理解 |
| 自然文の意味 | 原文の言語点検と独立した意味期待、機械実行を組み合わせる | 原文の正しさと自然さ、受理、対象と量と順序と時機、意図した結果 |
| 機械的な網羅 | 静的検査、モデル検査、標準ブラウザrunnerをActionsで実行する | 全能力、全命令と式とイベント、全フィールド、境界、編集原子性、保存と取込と出力 |
| 素材と音声 | ブラウザの実デコード、出力記録、実ファイル比較 | 元素材の同一性、音声の実出力、順序、待機と停止、埋込と持出し |

実操作は、新規作品から始める。標準QA作品の読込、素材ファイルの取込、実ファイルの保存は、制作UX開始の必須条件にしない。ファイル処理の機械的な成否はActionsが担い、UXでは制作に必要なボタンと説明の発見性を確認する。

機械結果を実操作結果や実児童の成功へ読み替えない。成人による児童目線の代理評価を行う場合は、その評価方法と限界を明記する。実際の児童の理解や自由作文全般の成功率を、代理評価だけで保証しない。

## 3 制作UXの有限なシナリオ

精密な型、全境界、全フィールド、ファイル入出力の全分岐を各シナリオへ追加しない。次の8本で制作の一連を観察し、機械的な枝は対応するActions検査へ渡す。

| ID | イメージと制作 | 必須の観察 |
|---|---|---|
| UX-J1 最初の作品 | クリックに反応して移動し、指定した台詞を話す作品を作る | 初見の目的から書く場所や置く場所を発見できる。対象、できごと、量、台詞が意図どおりで、実行から編集へ戻れる |
| UX-J2 動きと時機 | 押すたびに動く作品と、押している間だけ動く作品を作る。方向、向き、回転、待機、時間をかけた移動を読み分ける | 自然な文から方向、量、時機を予想できる。反復と継続の範囲が読み取れ、止まったことが分かる |
| UX-J3 登場人物と描画 | 初期の登場人物と画面上で追加した登場人物を順に動かして話させる。隠して戻し、図形を描く | 登場人物や対象を取り違えない。文と画面の順序、姿、描画が対応する。素材や描画の入口を発見できる |
| UX-J4 点数と持ち物 | 点数を増やし条件で分岐する。持ち物へ一つ挿入し、順番に調べて話す | 数と単位、条件の答えと引用文字、繰返しと分岐の範囲が分かる。初期値や候補の案内で意図を保てる |
| UX-J5 会話 | 名前を尋ね、答えを待ち、その答えに挨拶をつなげる | 正しい自然な原文で質問、待機、回答、挨拶が実現する。引用文字を保持し、入力や変換中に誤送信しない |
| UX-J6 再利用と仲間 | 手順と計算を定義して使う。複数の登場人物へ知らせ、処理の完了を待つ。分身を作り、分身だけを動かして消す | 定義、引数、答え、所有者、知らせの範囲、元と分身を理解できる。自然文と独立したブロック制作の結果が一致する |
| UX-J7 意図を保って直す | 制作中の誤りと長い台詞を使い、案内から修正する。取消と戻す操作、ブロックの一フィールド編集を行う | 案内が国語として分かる。製品固有の言い方を当てる作業にならない。原文、意図、選択とフォーカスが壊れない |
| UX-J8 作品を確かめる | 作った作品を実行し、結果や失敗位置を確認する。モードと表示量を選び、編集へ戻る | 書いた文と動作が対応する。何が違い、どこを直すか分かる。表示、反応、説明の入口が制作を妨げない |

### 3.1 共通の実施手順

1. 対象版を固定し、新規QA作品を開く。使う意図、原作文、事前予想、必要な初期状態を固定する
2. 実行結果を見る前に、原作文の国語的な正しさと意味を記録する
3. 原文を見える入力欄へ入力する。本文のみの欄か全コードの欄か、選択中のイベントや対象との対応を確認する
4. 実行結果を先に固定した意図と比較する。対象、量、順序、時間、範囲、引用文字を確認する
5. 別の初期状態から、同じ意図をブロックで独立に作る。コードから変換したブロックだけを独立制作と数えない
6. 必要な一連が観察できたら、そのシナリオの実施を閉じ、合格か不合格かを別に判定する。失敗の深掘りで独立した残りのシナリオを止めない

実施中は、操作と待ち時間、読み直し、選択の取り違え、繰返した操作、修正の理由を必要な範囲で記録する。人が考えた時間や通信待ちを製品の反応時間に加算しない。時間や回数の製品合否閾値は、承認済みの仕様を使用し、検査中に新設しない。

実OSの日本語入力、変換、キーボード、実窓での見え方や操作感は、使用した機材と観測方法を明示する。合成された入力イベントを、実OSの入力体験の代用として合格にしない。

## 4 Actionsの受入グループ

以下は受入グループである。既存workflowとrunnerを再利用し、必要な差分を追加する。全件を手操作へ戻すための表ではない。

| ID | 機械的に検証する範囲 | 必須の合格証拠 |
|---|---|---|
| A-BASE 対象と能力 | 製品とテストの版、素材とfixtureのハッシュ、能力集合、全ブロック定義、保存契約、必須jobの集合 | 基準版との対応表、差分とテストの結合、必須項目の欠落がないこと |
| A-NAT 原作文と意図 | 凍結した正しい自然な原作文と補助定義を無変更で入力し、受理した後に実行する | 原文一致、受理、独立した期待との結果一致。原文を保存できたことや安全に拒否したことだけを成功にしない |
| A-SEM 意味 | 全命令、全式、全イベント、数、文字、真偽値、リスト、数量と単位、所有者とスコープ、定義と引数、同期と分身 | 各ケース固有の入力と期待、適用される枝の結果。モデル検査とブラウザUI検査を分ける |

| A-UI 表示と入力機構 | 全定義と文脈とページとフィルタ、意図語検索、長文、表示幅、ズーム、スクロール、フォーカス、当たり判定、キーボード、合成入力イベント、配色とクリップ | ブラウザtrace、スクリーンショット、位置と値のassert。自然さ、主観的可読性、実OS入力はUXにも残す |

| A-IO 保存と持出し | UI保存と実download、再読込、書きかけ本文と定義、破損と未知契約と過大入力の拒否、未保存保護、autosave、復元、単体書出し、Offline、埋込 | 実ファイル、本文、素材、所有者、下書きの一致と拒否原子性。内部serializerだけでUI保存を合格にしない |
| A-EVIDENCE 結果品質 | 対象版とrunとattemptの結合、期待と実測、成果物、欠落、重複、skip、timeout、集約の負例 | 同じ対象版の必須結果が揃い、欠落や実行不能が成功へ変わらないこと |

### 4.1 ケース固有の条件を維持する

命令と式は、独立した標準QA初期状態を使用し、そのケースに必要な対象、定義、変数、素材だけを追加する。通常命令の後続マーカーは、その命令の実行到達を確認するために用いる。停止や返却など、後続しないことが仕様となる命令では、その期待に従う。

式では、値の候補、対象、型、単位、状態、実行結果など、その式固有の期待を確認する。すべての式へ全履歴、全表示幅、全型、全不正文脈、ステップ実行、任意の後続マーカーを一律に付け足さない。これらの網羅は該当する受入グループで担う。

イベントでは、それぞれに必要な一致と非一致、押下と保持、並行、変更前後、元と分身の条件を確認する。境界では、仕様上の合法な値を使い、上限を縮小したりtimeoutを短くしたりして通過させない。

### 4.2 原作文コーパスの設計

クリック、キーの一回と継続、複数対象の順序、表示と描画、条件と反復、変数と単位、リスト挿入と走査、質問と文字連結、手順と計算、通知と全員の完了待ち、分身を含む代表的な制作意図を扱う。

代表12意図をコードとブロックの各12経路へ対応させる。読解の意味差を扱う8対の期待も保持する。意図や意味差の数を満たすだけでなく、対応表で各項目の内容を照合する。

原文、補助定義、初期条件、意図、期待は、製品の結果を見る前に固定する。主原稿だけでなく、必要な手順や関数の定義と単位も入力に含める。両モードへ同じ意味期待を使用する。正しい自然文が受理され、意図した結果になることを正の受入テストにする。

文の曖昧さ、誤り、不足は別の負例とし、分かりやすい案内と安全な非破壊を確認する。正しい文の拒否を負例へ移して成功にしない。テストデータは公開許諾された人工的なQAデータだけを公開コーパスへ含める。

## 5 標準テストframeworkとrunner

### 5.1 ケースの共通契約

各ケースは、実装するテスト層に関わらず、次の項目を持つ。

| 項目 | 契約 |
|---|---|
| caseIdとrequirementIds | 安定したケースIDと、対応する受入グループや要件のID |
| layer | static、model、browser-ui、media-output、file-ioなど、実際に検証する層 |
| target | 製品commitと製品ハッシュ、テストcommit、保存契約の版 |
| fixture | fixture ID、内容ハッシュ、初期条件、追加する条件、公開可能性 |
| input | 無変更の原文、補助定義、またはUI操作列。文字列を正規化する場合は仕様上の規則を明記する |
| expected | 製品の実測から生成していない独立した期待。結果、順序、単位、対象、拒否、原子性など |
| execution | 実施状態、結果、実行層、環境条件、run、attempt、実行不能や不足の理由 |
| artifacts | 必須成果物の種類、相対的な成果物名、内容ハッシュ。公開成果物には非公開データを含めない |
| dependencies | 必要な定義、素材、コーデック、観測手段。条件が足りない場合の扱い |

ケース定義に実行前提と期待を持たせ、runnerが期待値を製品の出力から書き換えない。テストが同じIDを重複して登録した場合、または必須IDが未登録の場合は集約で失敗にする。

### 5.2 runnerの共通ライフサイクル

1. **収集**: 受入対応表から必要なケースと層を列挙する。担当層、依存、重いケースの区分を確定する
2. **事前確認**: 対象版、製品ハッシュ、fixtureハッシュ、実行環境、必要な観測手段を照合する
3. **初期化**: ケースごとに独立したQA状態を用意する。ブラウザUI能力を検証するケースでは、通常のUIから新規作成や読込を行う
4. **操作**: 固定した入力を実行する。ブラウザUIケースは見えるcontrolsを操作し、内部APIの直接実行をUI操作済みと数えない
5. **照合**: 受理と実行を別にassertし、独立した期待に比較する。拒否のケースは非変更と履歴も確認する
6. **記録**: 実際の層、結果、trace、画像、音声、実ファイルを必要な範囲で保存する。結果と成果物を同じケースと版へ結合する
7. **後処理**: 各ケースの資源を片付け、次のケースへ状態を持ち越さない
8. **集約**: 必須ケース、必須成果物、版、結果の完全性を検査する。不足やskipを合格へ集約しない

モデルだけで証明できる内部予算やvalidatorの検査はモデル層で行う。モデル試験の成功をブラウザ操作の成功へ読み替えず、同じ要件に必要なUI側の検査を残す。

### 5.3 ブラウザrunner

ブラウザとバージョン、OS、CSS viewport、device pixel ratio、ズームを記録する。物理窓の試験、viewportエミュレーション、スクリーンショットの縮尺を区別する。表示検査では少なくとも代表的な横幅1366、1024、390を扱い、それぞれの測定条件を固定する。

長文編集は64文字と385文字、100％表示と見わたす表示、基本と詳細、横幅1366と1024を組み合わせた16条件を維持する。表示幅390の検査は別の小幅レイアウト条件として行う。長文の本文は公開可能な人工データを使用し、内容の一字単位の保持、末尾到達、全文編集、取消と履歴を確認する。

クリック、入力、ドラッグ、Tab、モーダル、検索、候補選択、切替、実行を通常の操作経路で行う。選択対象と入力対象が一致することを確認し、スクリーンショットだけでなく、焦点、値、当たり判定、操作後の本文や状態をassertする。

UIを検証するケースは、製品のDOMや内部状態を直接書き換えて作品を完成させない。機械fixtureを直接扱うモデル検査は別層として明示する。実OSの日本語変換や人の読みやすさは、このrunnerだけでは完了としない。

### 5.4 ファイルと音声のrunner

ファイル検査では、実際の保存、ダウンロード、再読込、書出し、Offline起動を自動化し、ファイルの存在と内容を検査する。保存された未完成原文、素材、所有者、定義下書きも照合する。失敗時は本文、選択、履歴、未保存状態が意図せず変わらないことを確認する。

音声検査では対応形式の実デコードに加え、ブラウザが出力した音を観測し、音量、音程、再生順、待機と停止を確認する。出力の観測手段が利用できない場合は実行不能として残す。無音環境で再生関数が完了しただけでは実出力の合格にしない。

### 5.5 jobと成果物の集約

静的、モデル、通常ブラウザ、音声、重い境界、ファイルIOを、依存関係に従って分割する。shardはケースIDの決定的な集合を持ち、重複と欠落を検出する。実行量と成果物の保存量は利用できるrunnerと容量に合わせて設計し、無制限を前提にしない。

集約jobは同じ修正版について、既存の必須検査と新しい回帰を確認する。別commitの成功、再試行前の成果物、必要な検査のskip、timeout、成果物欠落を成功へ変換しない。既知失敗をxfailやcontinue-on-errorで記録する場合も、必須受入が失敗している事実を集約へ伝え、リリース合格を遮断する。

集約器自身に、欠落、重複、版不一致、誤ったfixture、skip、期待改変、成果物不一致を投入する負例を用意する。すべて緑になったように見える誤集約を検出することも必須検査とする。

## 6 従来のUI観点と担当層の対応

## 7 実施完了と合格の定義

### 7.1 実施状態と結果を分ける

実施状態はNOT_RUN、IN_PROGRESS、DONE、BLOCKEDを使用する。結果はPASS、FAIL、REVIEW、UNDETERMINEDを使用する。必要な観察を終えて不合格を確定したケースは、DONEかつFAILになり得る。

親要件の一部を観察しただけで全条件をDONEにしない。一方、親要件に未実施部分があるために、個別に判定できた検査を未実施へ戻すこともしない。原経路の失敗で後続不能になった枝は、依存によるBLOCKEDとし、実施しなかった条件を記録する。

不足は「証拠があるが未統合」「必須操作が未実施」「観測手段が不足」「前提の失敗で後続不能」を区別する。要件に根拠のない追加確認を、完了の必須条件にしない。

### 7.2 一巡の実施を閉じる

8本の制作シナリオと全Aグループの必須条件について、実施結果と残条件を確定する。すべてDONEなら必須範囲の一巡を完了したといえる。BLOCKEDがある場合は、実行可能分の結果とBLOCKED一覧を報告し、全必須完了とはしない。

BLOCKEDには対象、未実施の条件、原因、担当役割、解除条件を記録する。未着手や実行不能を成功へ変換しない。子ケースと親要件の重複を含む表の行数を、そのまま完了率の分母にしない。

### 7.3 全体合格

次のすべてを満たしたときに全体合格とする。

- 正しく自然な原作文が受理され、独立した意図期待を実現する
- 同意図をブロックで独立に作れ、範囲と意味を理解できる
- コードとブロックの完全意味互換が必要な全ケースで成立する
- 基準版の機能を保持し、必須の機械検査がすべてPASSである
- 必要な制作UXの証拠が揃い、必須FAIL、BLOCKED、REVIEWが残らない

Actionsがすべて成功しただけで、自然文の国語品質や制作UXを合格にしない。見た目の版番号が同じでも、製品ハッシュが異なる結果を混ぜない。

## 8 製品修正と再検証の順序

1. 日本語の意味、コードとブロックの共通意味、編集と保存の契約を仕様へ整理する。修正方針と受入テストの期待を先に確定する
2. Actionsのframework、標準runner、要件対応表を整備し、修正前に捕捉すべき失敗と、修正後に通るべき独立期待を用意する
3. 修正ブランチで実装し、必要な回帰を追加してpushする
4. Actionsの失敗とskipを、製品不具合、harnessまたはfixtureの不備、環境と依存、未実装に切り分ける。期待を誤った実測へ変更せずに修正し再実行する
5. 同じ修正版について既存必須検査と新しい必須回帰がすべてPASSになり、集約で欠落と版違いを拒否することを確認する
6. 必要CIが成功した版をmainへmergeし、公開版を配備する。配備された製品のハッシュを照合する
7. 通常の利用条件と使用環境を確認したうえで、新規作品から必要な制作UXを実操作する。ファイルIO全体はActionsで担い、UXへ重複させない
8. UXで不合格が出た場合は、修正ブランチで直し、関係する機械回帰と影響する制作シナリオを再検証する。広域の機能退行はActionsの全回帰で検出する

再検証では、原失敗、修正差分、新結果を版ごとに保持する。毎回全要件を手操作でやり直すのではなく、失敗とその影響範囲のUXを重点的に確認する。必要なUXが未観測なら、CI成功だけで全体合格にしない。

## 9 担当役割

| 役割 | 責任 |
|---|---|
| 仕様担当 | 自然日本語の意味、共通意味表現、可逆編集、機能保持、修正の受入条件 |
| 実装担当 | 修正ブランチ、回帰テスト、CI不具合の切分けと修正 |
| Actions担当 | 標準runner、全機械ケース、環境と資源、成果物、集約の完全性 |
| UX担当 | 新規作品からの有限な制作シナリオ、原文と事前予想、通常操作と観察 |
| リリース担当 | 同一版の必要CI、merge、配備版照合、UX結果を含めた最終受入 |

## 10 公開用文書としての確認

本書には、製品の受入要件、一般的なテスト設計、担当役割、完了条件だけを含める。個人情報、個別端末の情報、認証情報、個人作品、非公開のファイル識別子、絶対パス、内部会話、個別の監査ログや証拠への参照は含めない。

公開するテストデータと成果物にも同じ条件を適用する。スクリーンショット、trace、音声、実ファイルへ個人情報や非公開データが混入していないことを確認してから公開する。

目的、機能保持、完全意味互換、自然原作文の受理と意図実現、有限な制作UX、全機械範囲、標準runner、証拠と完了条件、修正から再検証までの順序を本書の必須要件として照合する。この文書確認は製品検査の実行や合格を示すものではない。
