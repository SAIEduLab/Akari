# あかり1.0.2 公開用実装修正仕様

仕様ID: AKARI-PUBLIC-SEMANTICS / 版1.0

## 0. 目的と実装原則

小学生が想像したことを、国語教育として正しく自然な日本語で書いて実現し、読んだ文から動きを想像できる環境を目指す。Blockも説明書なしで同じ意味を組み立てられることを目標とする。

本書は製品の技術要件、再現用の例、受入テスト、実装候補を定める。掲載例の部品名と入力文字列は架空の固定テスト値であり、実際の利用者データではない。本文は実装済み・合格済みを意味しない。

1. Code/Blockは共通意味表現から実行する。文型・値穴・表示・検査・実行の役割定義を共通化する
2. 12例だけの全文一致特例で受理させず、助詞・語順・対象・単位・時間・範囲・反復・条件・手順・計算・リスト・知らせ・分身を一貫した構文で扱う
3. 未完成作文とBlockの穴を失わず保存できる。実行可能性の検査を作品保存の前提にしない
4. 機械で検証できる処理はCIへ配置し、人の評価は発見・言葉・読み・案内・操作感に集中させる
5. 能力削除、上限引下げ、未対応nodeの除外、失敗に合わせた期待値変更は禁止。旧版のファイル/構文互換を切る変更は許容するが、新版のCode/Block完全意味互換、新版内の保存/復元を必須とする

## 2. 共通意味表現の必須契約

### 2.1 正本と層

構成は次とする。名称は提案であり、既存コードへの適切な分割は実装担当が決めてよい。

```text
児童の原文 ─→ 損失のない字句/文構造（CST） ─→ 共通意味表現（Semantic IR） ─→ 検査済み実行計画
                                                    ↑          ↓
                                                Block編集    自然な文の表示
```

- 保存上の正本は、原文を持つ編集文書と、同じ版に結び付く意味構造/下書き。古い解析キャッシュを信頼して実行しない
- 実行上の正本はSemantic IR。CodeからとBlockからで異なる解釈器を使わない
- CSTは句読点、原文の語順、改行、コメント、引用内の文字、選択位置との対応を保持する
- IRは意味だけを持ち、対象ID、操作、型、数量/単位、条件、範囲、並行性、待機、参照先を明示する
- 原文解析の失敗時にも原文を編集・保存できる。無効部分を含む下書きを実行可能IRと混同しない。無編集でモードを往復した場合はsourceTextをそのまま使い、canonical再生成を挟まない
- 既存ASTをIRとして拡張してよい。全面書換えを目的にせず、既存`actorRef`、`QuantityLiteral`、`Broadcast`、`WaitBroadcastGroup`等の能力を再利用する

### 2.2 最小データモデル

```ts
type EditorDocument = {
  documentId: string;
  revision: number;
  sourceText: string;
  sourceMap: SourceMap;
  units: EditableUnit[]; // 複数イベント、継続ルール、手順、計算
  drafts: DraftRecord[];
};
type SemanticNode = {
  id: string;
  operation: string;
  actor: ActorRef;       // runtime self / 明示した部品ID
  roles: RoleBindings;   // target/value/direction/duration/rate/condition等
  suites: Suite[];       // 順序と入れ子を保持
  origin: OriginRef;     // 文書版・原文範囲。意味比較からは除く
};
type ParseResult =
  | {status:'complete'; document:EditorDocument; ir:ProgramIR; diagnostics:Diagnostic[]}
  | {status:'draft'; document:EditorDocument; diagnostics:Diagnostic[]}
  | {status:'ambiguous'; document:EditorDocument; choices:MeaningChoice[]};
```

実装名・型言語は拘束しない。重要なのは、選択中の行/イベントと原文の行番号を同一IDとして使わないこと、複数イベントを単一Scriptの偶然の範囲に閉じ込めないこと。

### 2.3 解析の決定手順

1. 文字列・名前引用・コメントを損失なくtoken化し、引用外の文境界と最上位見出しを先に確定する
2. 記号表を使い、主体・対象名・数量句・方向句・時間句・述語を候補にする。各述語の役割契約で必要要素・型・助詞・重複を検査する
3. 自然な語順変形は同じ役割へ束縛する。複数の表面解析が同じIRになるなら一つにまとめる
4. 異なるIRが複数残れば、文型の登録順や確率で一方を選ばず意味確認を出す。候補0なら未完成・型矛盾・未対応表現を分ける
5. 範囲、対象参照、単位、定義引数、通知の参照を検査してから実行可能とする

解析に外部AI呼出しやネットワークを必須にしない。既存のオフライン能力を保つ。parserは候補数/深さのbudgetを持ち、memoization等で同じ区間を重複解析しない。100,000文字/本文・128深さ等の既存上限内の正当な文を、無制限backtrackingで実用不能にしない。複数解釈が多い場合は原文を保持した診断で停止し、任意解釈を実行しない。

### 2.4 不変条件

| ID | 必須条件 |
|---|---|
| SEM-01 | `meaning(parse(code)) = meaning(decode(block))`。同じ初期状態・入力・論理時刻で実行トレースが一致する |
| SEM-02 | 読める文とBlockで、対象・操作・量・単位・時機・順序・範囲・条件・待機対象が同じ |
| SEM-03 | Code→Block→Codeを無編集で往復して、原文の文字列・コメント・名前を失わない。原文表記も保存する |
| SEM-04 | Block編集後に再解析して、意図したIRだけが変わる。他のイベント・対象・原文に変更を漏らさない |
| SEM-05 | 完成部分と下書き部分を識別できる。未入力の値を0/真/空文字へ捏造しない |
| SEM-06 | 意味を一つに決められない文を、文型の照合順だけで黙って実行しない |
| SEM-07 | 取消・拒否・Undo・Redo・復元の後、原文/IR/選択/診断/dirty状態が同じrevisionに属する |
| SEM-08 | ランタイムの分身・発言・一時値を設計データに逆流させない |
| SEM-09 | 対象の名前変更で参照先は変わらない。同名や曖昧な参照は選択肢として提示する |
| SEM-10 | Code/Block/復元後は同じ実行可能性の診断を出す。作品保存/読込の拒否ゲートは構造・安全性・物理上限とし、型/文脈等の実行意味違反は安全な下書きとして保持する。実行/実行HTML書出しでは意味違反を拒否し、拒否は原子的 |

意味比較は文字列一致ではなく、正規化したIRと実行トレースで行う。生成されたBlockをCodeへ戻しただけの試験は、独立したBlock制作成功の代わりにはならない。

## 3. 日本語を意味へ結び付ける仕様

### 3.1 字句、表記、引用

1. 引用外の全角/半角の数字、許可した演算記号、句読点の表記差を正規化してよい。ただし原文と位置対応は保持する
2. 引用文字・登録名の内部を、文型検出、助詞分割、接続語除去、全角化、大小文字変換の対象にしない
3. 「」内の読点・句点・助詞・`※`を命令区切りにしない。文字列内の引用符と改行は可逆に保存する
4. 改行を含む文字は、Blockの全文編集からそのまま入力できる。Codeも開いた「から閉じる」までを複数行の一つの文字tokenとして読む。引用内のLFと行頭空白は内容であり、文の字下げ処理から除外する。内側の引用符とバックスラッシュは既存のエスケープを使い、BlockからCodeへの変換で自動的に付ける。canonical表示は実改行を用い、見やすい囲いで一つの文字と示す。文字内容のLFを消さない
5. 文字の内部では改行・結合文字・絵文字を保持する。表示上の省略と保存文字列の切捨てを混同しない
6. 名前を「おじぎ」と引用したとき、手順を要求する文脈なら手順名参照として束縛できる。児童に`【】`への機械的置換を強制しない。台詞文脈の「おじぎ」は文字列のまま
7. 助詞の入った登録名は最長一致だけに依存しない。記号表と引用境界で候補を得て、型と役割で決める。同順位で複数の意味が残れば選択を求める
8. 句点あり/なし、自然な読点位置の差は意味を変えない。ただし読点だけで反復範囲・条件範囲を推測しない
9. 字下げや囲いは範囲の手掛かり。Blockは自動整形する。Codeでは全角空白/タブをただ「不正」とするのでなく、まとまりのプレビュー付きで揃える提案を出す。自動補正は確定前に示し、原文を残す
10. 数量の基本語彙はアラビア数字（半角/全角、小数、負数、式）を必須とする。「一つずつ」「一度」「たび」「体」など、文型として現れる助数表現は構造的に扱う。一般の漢数字すべての受理は未実装なら保証しないが、「三体」のような自然な拡張を加えるときは数量字句規則として追加し、個別文の別名にしない

### 3.2 文節の意味役割と語順

単純な末尾の正規表現だけで文全体を決めず、述語ごとの役割表を共通定義する。各役割に許容助詞・型・単位・必須/省略条件・重複規則を持たせる。

| 役割 | 例 | 意味 |
|---|---|---|
| 動く主体 | `あかりは` / `あかりを…動かす` | actor。現在選択中の部品に勝手に置換しない |
| データの変更先 | `点数を` / `点数に…足す` | data binding。主体と区別 |
| 方向 | `画面の右へ` / `前に` | world方向 / 主体の向き基準を区別 |
| 距離 | `30歩` | displacement |
| 移動時間 | `2秒かけて` / `2秒で` | duration。待機と区別 |
| 速さ | `1秒に30歩の速さで` | rate(distance/time) |
| 回数 | `3回` | 0以上の整数。処理全体の範囲を伴う |
| 個数 | `分身を3体` | 作る個数。歩・点・秒と混同しない |
| 位置 | `2番目に` | 挿入位置。データ値2と区別 |
| 条件 | `点数が3点以上なら` | Boolean、境界を含む |
| きっかけ | `押すたびに` / `作られたとき` | edge event |
| 継続条件 | `押されているあいだ` | 状態条件、時刻積分 |
| 待合せ参照 | `その知らせを受けて始めたこと` | 特定送信の受け手群 |

役割の順が違っても、意味が一つなら同じIRにする。

```text
あかりは画面の右へ30歩動く。
あかりは30歩、画面の右へ動く。
画面の右へ、あかりを30歩動かす。
```

この3文は方向・主体・距離が同じ。これに対して`あかりは右に30度回る`は別の操作。`30歩を2秒で右へ`のような表現は、その助詞と述語が文として自然かを評価してから文型に入れる。全単語の並べ替えを無条件に許可しない。

### 3.3 対象と省略

- イベント見出しの主体を、その本文の既定主体とする
- `星は…`と明示した節では星が主体。続く`…して、…する`は同じ節の主体を引き継ぐ
- 同じまとまりの後続の省略文は直近の明示主体を継承し、Block上で「星は」等を補って可視化する。補いは意味表示であり、原文を勝手に改稿しない
- 条件・反復の子本文で変わった主体を、外の本文へ漏らさない。範囲の入口で既定主体を保存し出口で戻す
- 別イベントへ主体を引き継がない
- 手順の`自分`は呼出し時の主体。手順内の明示対象変更を呼出し元へ漏らさない
- 分身イベントの`自分`/`この分身`は当該runtime instance。元の部品IDとの違いを保持する
- 存在しない対象は実行せず、その名前と候補を示す。似た名前の部品を自動選択しない
- `作品の点数`、`自分の点数`を区別。無修飾名は既存能力契約の「反復項目→局所→引数→個体→作品」の順位で解決する。順位により一意に定まる参照を曖昧扱いしない。解決した所属をBlock/意味プレビューで見せ、別スコープを使うときは修飾で選べる。同順位の複数候補など真に定まらない場合だけ選択を求める

### 3.4 順序、接続、終わり

- `Aして、Bする`はAの完了後にB。Aが待機を含む手順なら手順完了まで待つ
- `そのあと、`、`それから、`、`次に、`、`最後に、`は同じ逐次まとまりで順番を表す。`最後に`を不要語として拒否しない
- `最後に`は作品全体・他イベントの終了を待つ意味へ拡大しない。局所的な逐次順序の終わりを表す
- `2秒待って、20歩動く`は待機後の移動。`2秒かけて20歩動く`は移動に2秒。`2秒後に20歩動く`は待機＋移動へ正規化できるが、可視プレビューで順を示す
- 吹出しが同じフレームで置き換わる場合も意味上の順序を保持する。読解用プレビューやステップで途中発言を確認できる。勝手な待ち時間を追加しない
- `同時に`は順次接続語ではない。並列機能として明確に定義されていない用法は、逐次実行へ黙って変換しない

### 3.5 できごとと継続

編集文書は複数イベントを含められる。T11/T12の全文を一度に入れたとき、最上位の見出しごとに本文を分ける。第2見出しを`もし`の孤立した枝として診断しない。

| 文 | IRと実行契約 |
|---|---|
| `作品を動かしたとき、あかりは、` | start。Runのたびに1回 |
| `あかりがクリックされたとき、` | 当該部品のclick。押していない間/長押しだけで余分に発火しない |
| `「空白」キーを押すたびに、あかりは、` | keyDown edge。OSキーリピートは新しい押下に数えない。離して再押下で再発火 |
| `「右」キーが押されているあいだは、…` | 継続条件。押下中だけ実時間に応じた速度。離したら停止 |
| `「出発」という知らせを受け取ったとき、星は、` | message。完全一致するフィルタ、対象ID、独立本文 |
| `あかりの分身が作られたとき、` | cloneStart。新しく作られた各分身だけ |

既存の背景変更・入力値変更等、32の対象/イベント組合せは維持する。代表表だけに減らさない。

継続の必須等価文:

```text
「右」キーが押されているあいだは、あかりは画面の右へ1秒に30歩の速さで動き続ける。
「右」キーが押されているあいだ、あかりは1秒に30歩の速さで画面の右へ動く。
```

`動く`でも状態条件と速度がそろえば継続意味は明確。`動き続ける`の語尾だけを実装の入口条件にしない。距離だけの`押されているあいだ、30歩動く`は、単発距離か反復か速度かが定まらないため確認を求める。30歩/秒に黙って補完しない。

速度はframe数ではなく論理時間差で積分する。pause中の時間を除外し、stop/restartでキー状態を漏らさない。画面右へは向き不変、前へは現在の向きを使う。T03の許容誤差±6歩を満たす。

### 3.6 回数、範囲、条件

- `AしてBすることを4回くり返す`はA+Bを同じまとまりとして4回
- `3回くり返す`＋字下げ本文はその本文を3回
- `「おじぎ」という手順を2回行う`は、手順を2回順番に完走する。意味上はCountedActionCallまたはRepeatCount(UserActionCall)へ正規化できる
- `3回前へ進んで、右に回る`のように範囲の読みが複数あるときは、図と短い文で「進むだけを3回」「進む→回るを3回」を提示する
- 0回は本文を実行しない。負数・小数の回数は実行せず「回数は0以上の整数」と該当穴を示す。上限値は維持
- `もし点数が3点以上なら`は`>=`、`3点より大きければ`は`>`。それぞれ境界値で独立テスト
- `そうでなければ`は同じ字下げ・同じまとまりの直前Ifだけに結び付く。孤立Elseだけを専用診断にする
- `…までくり返す`と`…まで待つ`、`…あいだくり返す`を区別する。すでに満たす条件での0回/即時完了を定義し試験する
- 条件の`かつ`/`または`/`ではない`は括弧と優先順位を持つ。曖昧な入れ子はBlockの囲い、Codeの括弧で可視化。Booleanを文字列`「真」`と同一視しない
- break/continue/forever、入れ子、空のelse下書きは保持する。未完成の本文を`何もしない`へ自動置換しない

### 3.7 値、単位、計算

`数`、`量(値,単位)`、`文字`、`条件の答え`、`リスト`を区別する。

1. `点数`を単位`点`で登録して初期値欄に`0`を入れた場合、その値は0点として束縛する。欄にも「0 点」と表示する。宣言だけ点で実値が無単位という状態を作らない
2. 同じ規則を初期化、代入、増減、比較、Code/Block両経路に適用する。`点数を0点にする`→`1点増やす`→`3点以上`でR417を出さない
3. 単位付き入力欄の裸の数は、その欄の明示単位を持つ。単位が決まらない一般式では勝手に単位を推測しない
4. 異なる単位の加減・比較を拒否する。`1歩＋1秒`を換算したり、片方を捨てたりしない
5. 単位付き量×無単位数、同単位量÷同単位量等の既存能力を保持する。一般の次元計算を実装しないなら、未対応な積を実行時に数へ剥がさず具体的に案内する
6. `個数とねだんをかけた数`はMultiply(個数,ねだん)。`AにBを足した数`、`AからBを引いた数`、`AをBで割った数`は、助詞で順序を決める
7. `AとBをかけた数を、答えとして返す`の読点を許容する。`答え`という語が質問の返事か関数の返却かは文脈で区別
8. T10の原文引数3・80と外側+10は無単位数の計算として250を得る。原作文の「円の数値として扱う」文脈を勝手に`円`型追加の前提に変えない。通貨単位追加は別の仕様拡張
9. 既存の三角関数、逆三角関数、乱数、平方根、べき、丸め、文字処理、リスト計算等を残す。読みやすい表現を提供しても高度機能を消さない
10. 表示精度と値の意味を分離する。計算内部、条件、保存値を見た目の丸めで変えない。詳細は8.3

### 3.8 文字の結合と質問

必須等価表現:

```text
答えに「さん、こんにちは」をつなげて言う。
答えと「さん、こんにちは」をつなげて言う。
答えの後ろに「さん、こんにちは」をつけて言う。
```

いずれもSay(Concat(answer, suffix))で、左から右へ結合する。`「さん、こんにちは」を答えにつなげて言う`は助詞が示す結合先/付加値を解釈し、同じ順になる。単語順のそのまま連結ではない。

- `＋`を使う数値加算とは独立した操作を持つ。`+`を通すために任意の型を文字列化する修正は禁止
- 質問中は当該タスクを待機し、回答後に後続へ進む。質問を直列化し、回答は質問したタスクの答えに束縛する。質問未回答で古い答えや他タスクの答えを使わない
- 回答は入力された文字列そのもの。空白・内部の「」・絵文字・改行を保持する
- テスト回答の文字列`テスト「青空」`に対して、結果は`テスト「青空」さん、こんにちは`
- データ値を文字へ変換する明示的な既存機能は維持する。リスト全体の発言が未対応なら、全文モニターや「一つずつ」に案内し、文字/数への黙変換はしない
- 複数質問の順番・停止・再実行の契約を既存テストで保持する

### 3.9 リスト

- `持ち物の2番目に「かさ」を入れる`は既存2番目の前へ挿入。元の項目を失わない
- `持ち物の2番目を「かさ」に変える`は置換。助詞`に`/`を`と述語を区別
- `持ち物を先頭から一つずつ見て、次のことを行う`と`持ち物の中身を先頭から一つずつ見て、次のことを行う`は同じForEach
- `今見ているもの`はその反復の現在項目で読み取り専用。入れ子では最も近い反復を指す。外の項目を使う場合は名前を付けて選べる。項目binderへの代入は拒否し、元リストを変える操作と混同しない
- `今見ているものの値を言って、2秒待つ`は発言後に2秒。最後の要素にも待機を適用する
- ForEachは開始時のdeep copyによるsnapshot順を採用する。途中で元リストを変えても対象順/回数を変えない。UIの補足で「見始めたときの並び」と説明できること
- インデックスは1始まり。挿入は1〜長さ+1、参照/置換/削除は1〜長さ。範囲外・0・小数を勝手に丸めない
- データ作成UIは1項目1行の直接編集または明確な項目入力を標準にする。JSONや全角括弧の記法を知らなくてもリストを作れること。式入力は高度経路として残す
- 作成失敗は当該フォーム内に原因と対象欄を出し、入力を保持する

### 3.10 手順と答えを求める定義

- 「手順」は動作のまとまり、「答えを求める」は値を返す計算としてUIでも文でも区別する
- 引数は既存契約の値渡しを保持し、引数の局所変更を呼出し元の変数/リストへ漏らさない。引数は名前と値の対で束縛できる。`個数を3、ねだんを80として`は定義側の順番に依存しない。重複/不足/未知引数を個別に示す
- `「代金」で求めた答えに10を足して言う`はCallExpressionの外側にAdd(10)を置く。関数本体へ10を取り込まない
- 返却後の到達不能な命令、返却不足、定義未確定を区別する
- 計算は画面・作品データを書き換えない。手順は動作できる。関数を通すために純粋性検査を外さない
- 無引数と32引数上限、再帰/呼出し深さ、ローカル変数/リスト、返す値の型の既存能力を保持
- 名前と引数を変更したら参照箇所を一覧化し、ID参照で結合を保持する。壊れる変更は原子的に拒否または一括更新の確認を出す
- 定義本文の未完成も保存できる。未完成だから管理画面を閉じられず作品を保存できない状態を作らない

### 3.11 知らせと待合せ

- Broadcastは非同期に受け手を開始する。BroadcastAndWaitはその送信から始まった受け手群の完了を待つ
- T11の2文`知らせる`→`その知らせを受けて始めたことが全部終わるまで待つ`は、同じ送信IDに結び付ける
- 複数の同名通知が並行しても、別送信の受け手を混ぜない。名前一致だけを待機群IDにしない
- 直前の知らせを参照する場合、同じ逐次まとまり内で特定できることが必要。途中に別送信があれば直近の明確な送信。条件分岐等で送信が不確実なら曖昧性を示し実行しない
- 受け手0件は直ちに完了。停止・受け手のエラー・分身消去が起きたとき、待機を永久に残さず完了/中断/失敗を定義する。失敗を「全員正常終了」と表示しない
- 孫の通知は、受け手自身がそれを待っているなら受け手の寿命に含む。単に非同期送信した孫まで全体待ちに拡大しない
- T11では受け手を並行に開始し、1秒/2秒の順、最後の受け手終了前に「全員集合」を出さない

### 3.12 分身

- `自分の分身を3体作る`はcount=3のCloneCreateとして表す。1体しか作らない処理や3回の元イベント起動へ変換しない
- `あかりの分身`は元部品あかりから作るruntime instance。`自分`が分身でも作成元定義と現在instanceを区別する
- 数は0以上の整数。上限超過のとき一部だけ作ってから失敗しない。必要個数の余裕を事前に検査し原子的に拒否する
- cloneStartは新規各分身で1回。元のあかりの開始本文を繰り返し起動しない
- `この分身だけを消す`は当該instanceだけを削除。元の部品文脈では「ここは元のあかりです」と示し、元を消さない
- 分身の局所データは独立、作品データは共有という既存契約を保持。保存/再読込/単体HTMLの設計データへruntime分身を混入させない

## 4. 曖昧さとエラー修正

### 4.1 4種類を分ける

| 状態 | 例 | UIの動作 |
|---|---|---|
| 未完成 | `点数を` / 未入力の返す値 | 灰色の下書き。足りない役割を示す。保存可能、実行不可 |
| 意味が複数 | `3回進んで、回る` | 範囲の2候補を文と囲いで提示。自動選択しない |
| 意味矛盾/型違反 | `1歩と1秒を足す` | 2つの量と単位を示し、何が合わないか説明 |
| 製品未対応の表現 | 自然な意味は分かるが構文未実装 | 原文を保持し、理解できた役割と未対応箇所を示す。児童の日本語誤りと断定しない |

診断はコード番号だけでなく、1) どの文/穴か、2) 何が足りない/重複/違うか、3) 意図を保つ次の選択、を短く表示する。

例:

- 不適切: `P204 対応するもしがありません`（知らせ見出しを誤解析した場合）
- 適切: `ここから「出発」を受け取ったときの動きです。あかりの新しいまとまりに分けます`（有効な複数イベントはエラーにしない）
- 適切: `右へ動く速さがまだありません。「1秒に何歩」かを入れてください`
- 適切: `「点数」は点で数えます。ここには秒ではなく点の数を入れます`
- 適切: `くり返すのは「進む」だけですか。それとも「進む→回る」の両方ですか`

### 4.2 修正の原則

- 修正候補は原文の必要な範囲だけを書き換える。選択外の文章を失わない
- 量・時間・対象・条件・範囲を補う必要があれば、答えをユーザーに選んでもらう。点を外す、待ちを消す、3体を1体にする等は修正成功ではない
- 候補を適用する前に、変わる意味を短い文/Blockで見せる
- 「原文のまま考える」、取消、Undoを常に使える。候補を選ばず保存して続きに戻れる
- 原文・修正案・採用案は区別できる。旧診断を「現在のエラー」に残さない
- エラーがモーダル内にある場合はそのモーダル内で見える。背面の出力欄だけに置かない
- IME未確定文字、符号だけの数、途中の引用を即時確定値へ変換しない
- 修正支援の目標は180秒・3稿以内に意図を保って復旧できること。修正後に成功しても、元の自然文が受理されなかったことは別に記録する

## 5. Blockは日本語の別表示である

### 5.1 文として読む設計

- 見出し: 「いつ」「だれ」が一目で見えるイベントカード
- 命令: 「だれが」「どうする」「どれだけ」を左から自然に読む。単位は数値穴に接続し、離れたラベルにしない
- 条件/反復: 開始から終わりまで囲いを持つ。elseは対応するIfと視覚的につながる
- 手順/計算: 呼ぶ対象、渡す値、返る値を区別。値の穴に動作を接続できない理由を短く表示
- 名称と表示を変えても、同じ意味役割に同じ編集操作を使う。速度の数値だけ特別な壊れる入力経路にしない
- 主体を省略して見せる場合も、選択/読み上げ時に「誰の動きか」を確認できる
- 原文に対応する範囲を選択できる。BlockのクリックとCodeのハイライトが一致する
- 「かんたん」は最初に見せる情報量を減らす表示設定。能力を削る別言語にしない。「すべて」へ到達できる

### 5.2 初回操作の具体要件

1. 空の作品で対象/できごと/本文の関係が見える
2. 命令はクリックでも追加でき、ドラッグが必須ではない
3. 「ここに入れる」で前/後/内側が明確。拒否したとき元の命令が消えない
4. 値穴を押すと、その穴の型・単位に適した候補を出す。数/文字/値/計算を混同しない
5. Run/Stopと結果の場所が同じ画面で分かる。作品が動いている間もどの文が実行中か分かる
6. Codeへ切り替えなくても、できごと変更、主体変更、条件/速度/関数/リスト/通知/分身まで作れる
7. `Return`の返す値、未選択の対象、未入力条件はHoleで保持する。移動10歩/回転15度/待機1秒/大きさ100％/台詞こんにちはの既存明示既定値と区別する
8. 確定/取消を押す前に表示された数・単位・対象が、そのまま確定結果になる

### 5.3 検索

固定語`右に行きたい`、`小さくしたい`、`おおきさ`、`2番目に入れたい`、`点数`、`てんすう`、`おじぎ`、`代金`を通す。

- 正規表現ソースそのものを検索語辞書と見なさず、意味役割・操作・読み・目的の索引を持つ
- 「右に行きたい」から画面右への移動、「2番目に入れたい」から挿入へ案内する。「右に回る」「置き換える」は別候補として意味が分かる
- 登録名の検索結果は、そのデータ/手順を束縛した候補を優先し、汎用命令だけを出して終わらない
- 標準語彙のひらがな読みを持つ。ユーザー名の読みは必要なら編集可能な補助欄を持ち、推測した読みを正しいと断定しない
- 選択中の穴で使えない候補は理由を示す。隠す場合も「すべて」で見つかる
- 検索欄をクリックして入力した文字は検索欄へ入る。IME/Tab/Escape/検索クリアで本文へ誤入力しない
- 検索は候補の探索。検索語を本文へ勝手に挿入しない

### 5.4 旧設計から継承する編集保証

ブロックの対象・数量・期間・囲いの範囲・条件の枝は実行前に本文で確認する。予告のために実際の状態や乱数を実行しない。コードと同じ式を必要な穴へ入れ、リテラルへ畳み込まない。各節の選択・移動・1命令実行・注釈を保持し、型不明の式だけを理由に接続を拒否しない。未使用候補は使える対象・理由・移動先を示し、書きかけを保持する。検索は意図・かな・漢字・保存した手順／答え名から候補を探す補助で、検索語をそのまま実行する約束ではない。クリック・ドラッグ・キーボード、領域外・Escape・中断取消を維持する。

初回の案内量と能力集合を分ける。手順／答え編集でも、見出し、6行相当の本文、確定／取消、作品への復帰に到達する。1366×768・1280×720・1024×768・狭幅・200％で確認し、切替ボタン約240pxが本文を押し出す状態を再発させない。作品倍率と作業台倍率を区別し、全体表示・100％・元位置への復帰を保つ。長い名前・実フォント・絵文字・結合文字で、意味を示す助詞と単位を入力枠の外にも読めるようにする。

## 6. 編集を原子的にする

### 6.1 一操作のトランザクション

```text
begin(revision, selectedNodeId)
→ candidate IR/CST/draft を作る
→ 構造と意味/上限を検査
→ 変更範囲をpreview
→ commit(新revision, 1履歴単位) または cancel(元状態そのまま)
```

- 見出し変更はイベントIDを指定して行う。空本文/本文あり/本文だけ→できごと指定のすべてで同じ経路
- 文の意味を変更してから原文の変更部分を再印字する。既存`preserveBlockSource`の局所印字は活用可
- 原文範囲がない新規見出し等は、最小の所属単位を生成するfallbackを用意する。他の文書全体を整形して失わせない
- fallback後は再解析して意図IRとの差分を検証する。差分不一致なら元状態を保って内部障害として報告する。ユーザーにCode編集を強いない
- 1貼付・1確定で1結果。別イベントへ移ったら、そのイベントと本文を選択・表示する。空欄が残り再入力で重複する状態を防ぐ
- 連打/旧revisionの確定/別モーダルの確定は二重適用しない

### 6.2 Undo/Redo、取消、診断

- 操作前後の設計、原文、下書き、選択対象、関連素材参照を同じ履歴単位へ保存
- 無変更の表示切替を内容変更の履歴へ積まない
- 取消は元のrevisionの診断を再計算または復元する。失敗した候補の診断を再利用しない
- 診断のキーを`documentId + revision + contextRevision`とし、非同期結果が古い場合は現在画面へ出さない
- 有効なUndo/Redo履歴を自動保存から復元する。既存の30履歴上限を少なくとも維持する
- 履歴の素材は、現作品から削除されていても履歴が参照している間は保持する

<!-- DOCS-CONSOLIDATION-BEGIN -->
### 6.3 原文と未確定状態の継承

無編集の表示往復は原文・未保存状態・履歴・選択・スクロールを保つ。編集時は変更した最小範囲の語順・空白・コメント・名詞の区切りを保ち、広い再生成が必要な場合も最小の意味単位に限って再解析し意味の一致を検査する。－0の値は0と同じでも、原文は明示的な整形まで残す。拒否・取消・表示だけで履歴とRedoを変えない。

未完成原文・穴・未登録定義・未確定数値は、安全な編集状態として保存・復元できる。Runと実行HTML書出しは未確定解消と意味検査を必要とする。日本語IMEの変換中・ドラッグ途中は確定してから保存する。原文の解析失敗を偽のブロックや以前の正常本文の実行へ置き換えず、取消では直前の有効状態と所有者を戻す。現行LANGUAGEの保存・実行データ契約を採用し、旧設計の一律保存保留とは別の改訂として台帳に記録する。

## 7. 保存・途中作品・持出し

### 7.1 保存と実行は別ゲート

- **作品ファイル保存**: 編集文書、設計、原文、未完成の値穴/定義、素材を、安全で検証可能な形式にまとめる。Undo/Redoの永続化は自動保存・自動復元の必須要件とする。過去履歴を作品ファイルへ全量付けることは今回の最低要件に追加しない
- **実行/実行HTML書出し**: 実行対象に必要な意味検査を通ったときだけ行う
- 保存時に`flushActiveEditor()`失敗でただreturnし、ファイルを作らない経路をなくす
- 保存可能な原文は意味解析成功を要求しない。JSON構造、安全性、サイズ、素材整合性は必ず検査する
- 未完成保存後は「書きかけを保存しました。動かすには○○を完成させます」と明示する。保存失敗と構文未完成を混同しない
- 実行不能な下書きがあればRun時に該当箇所を示す。以前の正常版だけを黙って実行しない

### 7.2 保存形式の提案

```text
projectEnvelope
  contractVersions
  designProject
  editorDocuments[]  // 原文、ID、revision、下書き
  callableDrafts[]
  selectionAndView
  assets[]           // 現在＋下書きから到達する素材
  integrity          // 必須集合/長さ/hash
```

これは新規の形式設計。旧版との互換は切ってよい。新版で自分が保存した有効/未完成ファイルを完全に戻せることを優先する。自動保存recordはこのenvelopeにUndo/Redo/historyCursorと履歴専用の素材参照を追加する。作品ファイル24MiB上限とブラウザ自動保存の容量制約を混同しない。

- raw sourceが未完成でも下書きとして復元。parser cacheの内容だけで原文を復元しない
- 多数イベントの途中、手順作成中、計算の未入力返却、Blockの未確定数、全文文字編集後をそれぞれ保存
- 実行中に保存する場合は設計＋編集状態を保存。runtimeの分身/移動/発言/質問待機を持ち込まない
- 破損ファイル、未知契約、過大ファイルは現在作品を変更する前に拒否。読込候補が完全に検査できた後に置換する
- 同契約でappVersionだけ異なる場合の取り扱いは契約IDで決める。版文字列だけで無理由に拒否しない
- 既存24MiB等の作品ファイル上限は勝手に下げない。現在文書/下書き/素材を重複なく保存する。自動保存の履歴は差分・共有素材を使い、従来の30履歴を保持する。ストレージ容量不足は失敗として明示し、既存の保存済みrecordや編集中の作品を壊さない。容量を超える作品を黙って切り捨てない
- 保存成功表示はブラウザがdownloadを開始した事実と、自動保存の実書込完了を分ける。ユーザーのディスク確定を未検証で断言しない
- 自動保存は最後の編集revisionを記録し、古い書込完了が新しい内容の保存済み表示を上書きしない

### 7.3 保持とexport

画像/音声、衣装/背景/所属、引数/局所データ、名前と参照、原文文字、型/単位、選択とモードを保持する。実行HTMLは同じ実行計画を使い、オフラインで動作すること。未完成作品の実行HTMLが作れない場合でも、編集用作品保存は可能でなければならない。

## 8. 関連UIの欠陥修正

### 8.1 参照を壊す削除

衣装/背景/音/部品/定義/データの参照グラフを、CodeとBlock共通IRから作る。使用中の素材削除は、参照箇所と影響をその場で示して拒否するか、明示的な置換先選択へ導く。削除を通して次のRunでS301にするだけでは不十分。

未完成原文で参照解析不能な場合は、潜在参照を捨てて安全と言わない。削除確認に不確実性を表示し、少なくともUndoと素材保持を保証する。明示的な名前参照が存在する素材は削除時に拒否すること。

### 8.2 結果と説明の可視性

- モニターと出力欄を同時に開いても、モニターを16pxの読めない領域へ潰さない
- flex/gridのmin-sizeとscroll ownershipを整理し、値行/全文ボタン/閉じる/確定/取消へ通常操作で到達できる
- 1366×768、1024×768、390×844は独立条件。500pxでの検査を390pxの検査に代えない
- メディア/データ/定義のモーダルのエラーは当該画面内に出す
- Manualの明色背景に白文字が重なる配色を修正。説明書を読めるようにすることと、説明書なしで作れることは別の受入項目
- 新しいアクセシビリティ目標は本文コントラスト4.5:1以上、大きい文字3:1以上を提案する。この数値基準と実際に読めるかのUX評価を分けて記録する

### 8.3 数値表示

三角関数などの浮動小数点計算について、数値の正確さと画面表示の読みやすさを別に検証する。表示仕様は以下とする。

- runtime値、保存値、比較、演算は従来の数値契約と精度を保持
- 吹出し/モニターの通常表示だけ、計算由来の浮動小数点ノイズを抑える。safe integerは全桁を保持し、非整数は原則12有効桁を上限とする表示用formatterを別設置
- `sin(30)`→`0.5`、`cos(60)`→`0.5`、`tan(45)`→`1`、`asin(0.5)`→`30度`、`acos(0.5)`→`60度`を新表示契約の例として固定
- 丸めが発生した値は詳細に「表示を丸めています」と実値を示せる。全文表示/コピーには何をコピーするかを明示
- 入力した長い数値literal、Codeのformatter、ファイルの数値、`文字(...)`やConcatの意味変換を表示formatterで勝手に変更しない
- ゼロ付近、負のゼロ、非常に大きい/小さい数、丸め境界、単位付きの表示を試験する。Infinity/NaNの隠蔽に使わない

### 9.1 UX-01: 空の作品、サンプル、吹出し

1. 「新しく作る」の標準は空の開始本文とする。対象/できごと/命令追加の案内を空状態へ表示する。動くサンプルは「お手本を開く」から明示的に選べる形で保持し、能力や教材を削除しない

3. 「作品を動かしたとき」と「クリックされたとき」を区別し、現在動いた本文を示す。不要な例は通常の削除＋Undoで外せる
4. 新規空作品からクリック専用を作った場合、Run直後は動かずクリック1回ごとに1回動く。テンプレートでは開始イベントの存在を発見できることも評価する
5. stage倍率と吹出しの文字/UI倍率を分ける。吹出しをstage端へ逃がす、上限幅で折り返す、全文表示を提供する等で対象を隠さない配置を優先する。縮小倍率41％、100％、狭い画面を別条件として検査する

CIでは新規の空状態、明示選択時だけのテンプレート、クリックのtrace、吹出し配置/overflow/操作到達性を検査する。人は空状態の発見、サンプルの区別、被覆と読みやすさを評価する。

## 11. 受入テストの設計

### 11.1 日本語による制作例テスト

付録AのT01〜T12と付録BのT13を入力fixtureにする。意味を満たすために日本語を機械向けの別文へ置き換えない。値、単位、対象、時間、順序、範囲を個別に照合する。T07の結果は数値3・単位点・標準表示「3点」を別欄に記録する。

各ケースの必須段階:

1. 例文をそのまま解析する。複数イベントも全文を投入する
2. IRが例の意図と役割表に一致する。受理だけをPASSにしない
3. 規定の初期状態と入力/論理時計で実行する
4. 期待値、対象不変、条件の別枝、非一致イベント等を確認する
5. IR→Block→IR、IR→自然文→IRの意味一致を確認する
6. 人の代表UX評価では、Codeを変換せず独立にBlock制作できるかも確認する。機械生成Blockを独立制作と呼ばない

| N22 | 同名通知の並行送信、入れ子ForEach、手順内の主体変更 | 参照/局所scopeを漏らさない |
| N23 | 上限N−1/N/N＋1 | 契約どおり、拒否後の設計/原文/履歴/素材が不変 |
| N24 | 誤ファイルを未保存作品に読込 | 原子拒否、元の未保存内容維持 |
| N25 | 構造は安全だが`1歩＋1秒`や関数内の動作命令を含む作文の保存→読込 | 下書きとして原文復元、同じ意味診断。Run/実行HTML書出しだけ拒否。保存読込を拒否しない |

### 11.4 期待結果の記録形式

各testは少なくとも`id, purpose, source, inputHash, fixtureHash, expectedMeaning, expectedTrace, actual, status, productHash`を持つ。時間の数値比較は機械の論理時計と可視の実押下時間を分ける。`PASS/FAIL/NOT_RUN/BLOCKED/REVIEW`と実施状態を混同しない。

実行トレースは以下のうち当該ケースに必要なものだけを記録する。

```text
logicalTime / taskId / nodeId / actorInstanceId / operation
inputs / outputs / dataWrites / position / direction
messageSendId / receiverTaskIds / waitCompletion
cloneCreated / cloneDeleted / visibleSpeech / questionState
```

すべての式に全項目を要求しない。型/数量は機械テスト、見える文章と結果は人の読解判定で役割分担する。

## 12. Actionsへ渡す機械検証と人の判定

意味・形式・保存・取り込み・書き出し・境界等の機械検証はGitHub Actionsで実行する。人の操作評価は読み、発見、言葉、案内、操作感に集中させ、ファイル処理の全ケースを手作業で再走する条件にしない。

### 12.1 機械に任せる項目

1. lexer/parser: 原作文、等価変形、負例、引用保護、複数イベント、CST位置対応
2. semantics: 型/単位/対象/名前/スコープ/関数純粋性/通知群/分身
3. codec: 全schemaのencode/decode/format/parse、原文保持、Hole、ruleを含む意味一致
4. runtime: 固定clockとinput traceによるT01〜T12、C74/Q76/E32、pause/stop、境界L38
5. editor integration: 見出し/速度/連続編集/取消/UndoRedo/IME compositionのモデル状態、診断revision
6. persistence: 有効/未完成の実download/readback、履歴を含む自動復元、素材、export、破損拒否、オフライン
7. presentation checks: 規定の画面幅での到達可能性、focus、contrast、overflow、数値表示、Manualの回帰
8. validator: 欠落、重複、古いcommit/hash、例外、timeout、skip、改ざんartifactをPASSにしない

既存workflowへ追加し、新言語だけのPASSで既存能力群を省略しない。Node単体、ブラウザ統合、OS/実IME/実聴が必要な試験の結果を区別する。

### 12.2 人に残す項目

- 意図だけを見て自然な作文を作れるか。語彙/助詞を不自然に製品へ合わせさせていないか
- 実行前に文/Blockを読んで、対象・量・方向・時機・順序・範囲を予想できるか
- 説明書や外部手順なしで候補を見つけ、配置・変更・実行へ到達できるか
- エラーから意図を保って直せるか。説明が専門用語や内部都合だけになっていないか
- 選択、フォーカス、ドラッグ、全文編集、結果表示が直感に合うか

人のUX評価では、入口発見90秒・最初の作品完成3分、意図を保つ修正180秒/3稿以内を目標とする。読解は前/右、向く/回る、押すたび/押しているあいだ、待機/移動時間、台詞/データ値、条件/else、入れ子範囲、対象切替の8対を用いる。全機能を手操作で再検査する完了ゲートは設けない。T01〜T12だけを暗記した人の成功を一般の直感性とせず、未見の意図から作文し、受理前に自然さを評価する。

### 12.3 「Scratch以上」の扱い

達成目標として維持するが、機械テストや成人による代理評価だけで達成宣言しない。実児童の比較評価を行う段階では、年齢/経験を記録し、同程度の未見制作課題で、説明量・達成率・初回所要時間・助けの回数・読みの正確さ・修正時の意図保持を比較する。課題順による学習を入れ替えて統制する。

比較人数や統計基準を本書で後付け確定しない。実施前に評価計画を決める。未実施なら「児童UX未検証」と明示する。子どもの個人情報をテストfixtureや公開artifactへ含めない。

## 13. 能力非縮小の確認

能力非縮小の正本は`audit/fixtures/1.0.2-baseline-capabilities.json`の260能力ID全行である。C74（命令）＋Q76（式等）＋E32（対象/イベント）＋L38（制限）は計220件の機械葉caseであり、260能力全体ではない。残る40能力にも移管先・受入証拠を必ず対応させる。新版の164schemaは別軸であり、能力数/葉case数と足して独立試験数にしない。

260能力の内訳は、command74、limit38、event32、builtin26、state22、operator16、expression7、sensor5（計220）と、runtime11、product11、scope5、save5、editor3、ast1、comment1、branch1、slot1、maint1（計40）。旧baseline fixtureのschema153と、基準1.0.2のfeatures manifestのschema164を混同しない。能力の独立baselineと現行schemaの両方へ対応を付ける。

- 現行`audit/manifests/features.json`でCOMMAND_CATALOG=74、LIMITS=38、schemaIds=164を静的確認した
- 新版のmanifestは旧能力ID→新版操作/役割/schema/実行test/表示routeの対応表を持つ
- 名前やschemaを統合・置換しても、旧能力の意味を落とさず1件ずつ移し先を示す
- 新しい能力は追加し、旧能力の行削除で総数を合わせない
- 高度な演算/全イベント/素材/音声/衣装/背景/入力部品/停止/clone/局所データ/関数/上限を保持
- 基本画面で隠すことは許されるが、正しい文脈から到達できること。検索で消えるのは能力維持ではない
- 境界の上限値を下げてテストを通さない。新しいdraft/historyの追加にも既存作品サイズ/機能を不当に狭めない
- 旧構文互換の廃止は独立した版変更として明示し、旧記法テストの削除理由を「能力廃止」と混同しない
- 新版で新規作成したCodeとBlockは完全意味互換。旧版拒否を新規作品の非互換の言い訳にしない

## 付録A. 日本語による制作例

以下は製品仕様の固定テスト例。架空の部品「あかり」「星」とテスト文字列を使う。各例は独立した作品状態から開始する。

- 移動例は開始位置/向きをfixtureへ記録し、意図した軸以外を変えないことを検査する
- T04/T11は「あかり」「星」を用意する
- T07は点数を用意する。型と単位は本文の契約に従う
- T08は持ち物を「本」「ぼうし」の順で用意する
- T10は追加定義の手順/計算を用意する
- T09の回答は固定文字列`テスト「青空」`であり、実際の氏名を使わない

### T01

**意図**: 登場するあかりが、クリックされるたびに画面の右へ30歩動き、「今日はどこへ行こう」と話す。押していないときは動かない。

**期待**: 1回のクリックで横位置+30、縦位置・方向は不変。2回で+60。台詞は指定どおり。クリック前と長押し中に余分な移動をしない。

```text
あかりがクリックされたとき、
  あかりは画面の右へ30歩動いて、「今日はどこへ行こう」と言う。
```

### T02

**意図**: 空白キーを一度押すと、あかりが上へ24歩跳び、0.5秒後に元の高さに戻る。押し続けても連続ジャンプしない。

**期待**: 1回の押下で縦位置−24、0.5秒後に元の値。長押しで再起動しない。離してもう一度押すと2回目が動く。

```text
「空白」キーを押すたびに、あかりは、
  上へ24歩動いて、0.5秒待って、下へ24歩動く。
```

### T03

**意図**: 右キーを押しているあいだだけ、あかりが1秒に30歩の速さで画面の右へ進む。離したら止まり、向きは変わらない。

**期待**: 速度30歩/秒、縦位置・方向不変、離した後に移動しない。実際の押下時間tを入力ログから求め、移動量30tとの誤差は±6歩以内。期待速度は結果から変更しない。

```text
「右」キーが押されているあいだは、あかりは画面の右へ1秒に30歩の速さで動き続ける。
```

### T04

**意図**: あかりが先に画面の右へ20歩進んで「先に行くね」と言い、そのあと星が左へ15歩進んで「ついていくよ」と言う。

**期待**: あかり横+20、星横−15、他の位置・方向不変。星の動作はあかりの移動と発言の後。画面で対象を取り違えない。

```text
作品を動かしたとき、あかりは、
  あかりは画面の右へ20歩動いて、「先に行くね」と言う。
  そのあと、星は画面の左へ15歩動いて、「ついていくよ」と言う。
```

### T05

**意図**: あかりが姿を隠し、1秒待って再び姿を見せ、「ただいま」と話す。

**期待**: 開始直後は非表示、1秒前に再表示・発言しない。1秒後に表示と指定台詞。隠しても編集上のキャラクターを失わない。

```text
作品を動かしたとき、あかりは、
  姿を隠して、1秒待って、姿を見せて、「ただいま」と言う。
```

### T06

**意図**: あかりがペンを使って、一辺20歩の正方形を描く。同じ「前へ進み右へ90度回る」まとまりを4回繰り返す。

**期待**: 中心を通る4辺、各20歩、4回の右90度回転。最後の位置は出発点、方向は出発時と360度の整数倍の差。画面右への平行移動に置き換えない。

```text
作品を動かしたとき、あかりは、
  ペンを下ろす。
  前へ20歩進んで、右に90度回ることを4回くり返す。
  ペンを上げる。
```

### T07

**意図**: 点数を0点から始め、3回の繰り返しで1点ずつ増やす。3点以上なら「できた！」、そうでなければ「もう一度」と言い、最後に点数を話す。

**期待**: 点数は3点。真の枝だけを実行し、標準表示は3点（数値3、単位点）。別試行で初期点数0、増加2回なら2点と偽の枝。条件や単位を黙って変更しない。

```text
作品を動かしたとき、あかりは、
  点数を0点にする。
  3回くり返す。
    点数を1点増やす。
  もし点数が3点以上なら、
    「できた！」と言う。
  そうでなければ、
    「もう一度」と言う。
  最後に、点数の値を言う。
```

### T08

**意図**: 持ち物「本・ぼうし」の2番目に「かさ」を入れ、先頭から一つずつ2秒ずつ名前を話す。

**期待**: 並びは本、かさ、ぼうし。元のぼうしを置き換えない。発言の順番と各待ち時間を画像で確認。反復中の項目は正しい現在値。

```text
作品を動かしたとき、あかりは、
  持ち物の2番目に「かさ」を入れる。
  持ち物を先頭から一つずつ見て、次のことを行う。
    今見ているものの値を言って、2秒待つ。
```

### T09

**意図**: 名前を尋ね、答えに「さん、こんにちは」を付けてあかりが話す。答える前に台詞を出さない。

**期待**: 質問が表示され、未回答中は待機。テスト回答「テスト「青空」」に対し「テスト「青空」さん、こんにちは」。引用符・空白・文字が壊れない。

```text
作品を動かしたとき、あかりは、
  「名前を教えてください」と尋ねて、答えを待つ。
  答えに「さん、こんにちは」をつなげて言う。
```

### T10

**意図**: 何度でも使う「おじぎ」の手順を作り、右に15度回ってから左に15度戻る動きを2回呼ぶ。引数付きの「代金」計算で3個×80円+10円を求め、値を話す。

**期待**: 無引数手順を2回完走し方向が元に戻る。値を求める定義の引数3・80で240、外側+10で250。作品の値や画面を副作用で変更しない。

```text
作品を動かしたとき、あかりは、
  「おじぎ」という手順を2回行う。
  個数を3、ねだんを80として、「代金」で求めた答えに10を足して言う。
```

**追加定義**:

```json
{
  "actionName": "おじぎ",
  "actionBody": "右に15度回って、左に15度回る。",
  "functionName": "代金",
  "argumentNames": [
    "個数",
    "ねだん"
  ],
  "functionBody": "個数とねだんをかけた数を、答えとして返す。",
  "currencyContext": "ねだんと送料は円の数値として扱う。例の意図の3個×80円+10円=250円を変更しない。"
}
```

### T11

**意図**: 「出発」と知らせると、あかりは1秒後に「準備できた」、星は2秒後に「準備できた」と話す。両方が終わってから「全員集合」と話す。

**期待**: 2受け手が開始し、1秒と2秒の順番。「全員集合」は遅い受け手の終了前に出ない。別の知らせではこの受け手を起動しない。

```text
作品を動かしたとき、あかりは、
  みんなに「出発」と知らせる。
  その知らせを受けて始めたことが全部終わるまで待つ。
  「全員集合」と言う。
「出発」という知らせを受け取ったとき、あかりは、

「出発」という知らせを受け取ったとき、星は、

```

### T12

**意図**: あかりの分身を3体作る。分身は20歩だけ右へ進み、1秒後に分身だけ消える。元のあかりは残る。

**期待**: 最大3体の分身、各+20歩。1秒後に分身0、元のあかり1体。分身だけのできごとが走り、保存作品に分身を持ち込まない。


## 付録B. T13: 継続移動の語順

```text
「右」キーが押されているあいだ、あかりは1秒に20歩の速さで画面の右へ動く。
```

右キーの実押下時間をt秒とすると移動量は20t歩。縦位置と向きは不変で、離した後は移動しない。機械テストは規定論理clockで照合し、人の操作評価では実押下時間を使う。T03の30歩/秒とは別fixtureにする。
